1 Scaffold the kit into your repo

Pick one. The npx way needs nothing cloned; the clone way runs the pure Node installer. Replace /path/to/your/repo with your project folder.

# A · Quickest — straight from GitHub, nothing to clone (needs Node 18+)
# Preview first (writes nothing):
npx github:kunalsuri/ai-fication-kit shazam /path/to/your/repo --dry-run
# Then install for real:
npx github:kunalsuri/ai-fication-kit shazam /path/to/your/repo
# B · From a local clone — pure Node stdlib (no npm install)
git clone https://github.com/kunalsuri/ai-fication-kit.git
cd ai-fication-kit
node install.mjs shazam /path/to/your/repo      # Node 18+

shazam is the one-shot entry point: it checks your repo, detects the stack, asks a couple of short questions, and stamps the kit's files. It stops right where the thinking begins — that's step 2.

2 Draft the maps

Open your repo in Claude Code (or your agent of choice) and run the cold-start command. It scans the code and drafts the map (~5 min), every claim tagged [inferred] — a plausible guess, not yet a fact.

/cold-start

Using Cursor / Copilot / Codex? They read AGENTS.md — paste .claude/commands/cold-start.md as a prompt to run the same pass.

3 Audit, then keep it honest

Open ai/guide/MODULE_MAP.md, set each module's Stability, and flip the rows you've confirmed from [inferred] to [verified] — that flip is your signature, and only a human may make it. Then cross-check every file-path claim against the real tree (deterministic, no LLM):

node install.mjs verify /path/to/your/repo
# add --strict to fail (exit 1) on stale claims, e.g. in CI

From here, build features safely with /add-feature. Lost about what to do next? Run node install.mjs doctor /path/to/your/repo — it tells you.

The one idea behind the kit

An AI agent that guesses a repo's map and then trusts its own guess is dangerous — it will confidently edit the wrong file. The fix isn't more docs; it's making every claim carry its provenance, with a human gate between a guess and trust. The kit keeps three kinds of knowledge strictly separate:

1 · Script observed
Facts

Scripts check what's really on disk — languages, build command, file paths. No LLM, nothing executed. Always true.

2 · Model inferred
[inferred]

The agent's drafts from /cold-start — "this module looks like auth." Plausible, useful, not yet trusted.

3 · Human verified
[verified]

You opened the file and confirmed it. Signed with a date. Agents are forbidden from writing this tag — the flip is yours alone.

Alongside provenance, each module gets a Stability: frozen (hands off), stable (change carefully), ours (active surface), and ? (unaudited — agents treat ? as frozen, so an unaudited row is safe by default). That's the whole trust model: scripts never guess, the agent never self-certifies, and you never have to trust either blindly.

The util belt

Every command is deterministic script behavior — no LLM is involved. They read files, write reports, and (with three documented exceptions: drift --git, audit --git, indepth) never even run git. --dry-run previews any command that writes. Run them as node install.mjs <command> /path/to/your/repo — the one exception is demo, which takes no target path (it uses a throwaway temp dir) and no flags.

The trust escape-hatch, and its lock. Re-runs are incremental: files you edited are kept, and files carrying a human [verified] tag are never overwritten — not even with --force. The only way through that child-lock is --force-verified, which prints every signature about to be lost and makes you type overwrite. Human audit work is the most expensive thing in the system, so it gets the strongest guard.

Why ROADMAP, WORKLOG & specs exist — the engineering loop

Getting the map trusted is a one-time thing (Basic track). What happens every day after is the engineering loop: each feature or fix runs the same closed cycle, and each stage leaves a durable artifact under ai/lab/. This is how the repo remembers what changed, when, under which spec, and who checked it.

SpecSPEC_*.md — no code before the human OKs it
→
Implementsurgical diff, Stability gates apply
→
ReviewREVIEW_*.md — fresh context, re-runs tests
→
Recordone WORKLOG row per unit of work

The three files, and how they link

  • ai/lab/ROADMAP.md — the plan, one row per feature. Two sections: Planned (rich, spec-grade entries so even a lighter model can implement cold) and Shipped (thin pointer rows). It's the cousin of WORKLOG: roadmap tracks features, WORKLOG tracks work.
  • ai/lab/specs/SPEC_<id>.md — the detail of record. When work on a Planned feature starts, its detail migrates out of the roadmap row and into a spec. No code is written before a human OKs the spec.
  • ai/lab/WORKLOG.md — the ledger, one row per unit of work. The episodic index: the one place that answers "what was done to this repo, and why?" A single feature may span several WORKLOG rows.
The trace (why the linking matters). When a feature ships, its Planned row collapses to a Shipped pointer that cross-links — by feature ID, never by copying fields — its SPEC_<id>.md, its WORKLOG.md row(s), and its PR. So ID → spec → work-unit → PR is followable in both directions. And because every one of those paths is backtick-quoted, verify --strict checks them like any other claim — a row whose spec or review vanished fails CI. The ledger cannot silently rot.

Three disciplines keep the loop honest, in the same spirit as the trust model:

  • The reviewer never shares the implementer's context. /review-change runs in a fresh session and re-runs the suites — a reviewer that read the implementation reasoning inherits its blind spots.
  • Reproduction before fix. /fix-bug refuses the shortcut that creates phantom fixes: a failing regression test is the proof the bug is understood, and it outlives the fix as a permanent guard.
  • Everything an agent writes into ai/ stays [inferred] until a human audits it — including WORKLOG and ROADMAP rows. Same gate as the maps.
